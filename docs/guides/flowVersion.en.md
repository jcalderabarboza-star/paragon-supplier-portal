## 1 · What this process is

A change to a process is a document of its own. It names one process and lists what it would add in front of acts that process already has: steps a person completes, checks the platform evaluates, and forks that decide which steps apply. A change can add a refusal. It can never take one away, and it cannot add a state, re-route an act or move a lane.

Each change is a **version**. Its label is `<shipped version>.<n>`: the first change drafted against a process that ships as version 2 is `2.1`, the next is `2.2`. The number counts per process and is never reused. The id is `fv-<n>`. The store assigns the id, the label and every stamp; the person drafting says only which process and what the change is called, or which version to start from.

A version moves through **Draft → In Review → Approved → Active → Retired**. **Rejected** is the only ending. Approving and activating are two acts: approving says the change is right, activating puts it in force. Rolling back is the same switch thrown back: **retire** returns the process to the shipped default, **restore** brings an earlier change back.

Who touches it: the **buyer's Compliance lane** holds all three permissions. `flow:draft` creates, saves, proposes and withdraws. `flow:decide` returns, approves and rejects. `flow:activate` activates, retires and restores. A lane cannot be the one that changes the process it is held to, so procurement, receiving, finance, planning and the requisitioner hold none of them. Admin and Super Admin hold them as they hold every buyer-side permission. The separation is between persons: whoever proposed a change may not approve it. Every seat can read the **Changes** tab.

Honest markers, stated plainly:

- **Content is written in Draft only.** From In Review on, a version is never edited and never deleted. A changed copy is made with **Start a draft from this version**.
- **Every act from proposing onward needs a named person and a stated reason.** A seat that names nobody is refused, and so is a reason left blank.
- **The change is checked against the rules three times:** when it is proposed, when it is approved and when it is activated — and once more when it is restored. Each time against the process as it is then.
- **At most one version of a process is in force.** Activating or restoring a version retires the one that was in force, automatically.
- **While a version is in force, an act with an added step in front of it is refused until the step is completed by its lane.** The document does not move. When the act succeeds, the completions are used up. Every event records which version of the process the act was taken under. The steps themselves are the *Step added by a change to a process* guide.
- **A version in force that no longer obeys the rules is set aside, by name.** The process then runs on the shipped default. The version is neither kept in force silently nor dropped.
- **Forks, checks and scans cannot be put in force yet.** A version that holds one is refused when it is proposed. Only Approval, Confirmation and Data capture steps can be composed.
- **Every act after drafting is taken in the review of a change.** On the **Changes** tab, **Review** in a version's row opens a drawer with the state, who drafted and who proposed the change, since when it is in force, **What this change does** in sentences, the steps it adds, **What the rules say now**, and the **History**. Its footer offers the acts the state allows, and every act asks a one-line reason first. Every seat can open the review; each act asks its own permission, and a seat without it reads which lane holds it. **Reject** and **Retire** are destructive: pressed, they ask, and the confirm is the destructive button.
- **Versions live in this browser only** (`localStorage`, key `paragon.flowVersions`), until a backend exists. They survive a reload. They are not shared with anyone and go when site data is cleared.
- **Nothing is seeded.** The list opens empty; every version in it was drafted in this browser.
- There is no user directory yet, so the named person is a sample identity adopted on the identity panel. A sample person may approve, activate and restore on a demo or preview deployment, and not on production.

**Forks**

- **At Draft:** `t_flowversion_save` — `flow:draft` — replaces what the draft says; the draft stays a draft. `t_flowversion_propose` — `flow:draft` — when the change is finished and obeys the rules.
- **At In Review:** `t_flowversion_approve` — `flow:decide` — when the change is right, by a person other than the proposer. `t_flowversion_return` — `flow:decide` — when it needs more work. `t_flowversion_reject` — `flow:decide` — when it is not wanted; this is the ending. `t_flowversion_withdraw` — `flow:draft` — when the author takes it back.
- **At Approved:** `t_flowversion_activate` — `flow:activate` — when it should be in force now. `t_flowversion_withdraw` — `flow:draft` — when the author takes it back to work on it.
- **At Active:** `t_flowversion_retire` — `flow:activate` — when the process should run on the shipped default again. `t_flowversion_supersede` — automation — when another version of the same process is activated or restored; nobody declares it.
- **At Retired:** `t_flowversion_restore` — `flow:activate` — when an earlier change should be in force again.

Creating and saving are refused for a seat that names no person (`flowversion_author_named`), as are proposing and withdrawing. Every decision from returning onward is refused for such a seat by `flowversion_decider_named`.

### t_flowversion_create — Create draft <!-- transition:t_flowversion_create -->

- **Step kind:** operator action (creation)
- **Role:** buyer · compliance (atom `flow:draft`; Admin and Super Admin hold it too)
- **From → to:** ∅ → Draft
- **Operator — where:** two entrances, both on `/buyer/process-flows` → tab **Changes**. (1) **New change** (top right of the page header) → the pop-up **New change** → **Create draft**. The pop-up is a dialog: it takes the focus, and Escape, the close button or a click outside closes it. The button stands in the header only while the **Changes** tab is open. (2) In the row of a version, column **Actions** → **Start a draft from this version**. There is no pop-up: the act fires when the link is pressed. A seat that does not hold `flow:draft` sees, in the header, **Changing a process is a Compliance action** with an *Awaiting Compliance* hand-off notice and no pop-up; in a row, the **Actions** column offers that seat **Review** only.
- **Operator — do:** (1) choose the process and name the change, then press **Create draft**. The change is created as an empty draft against the process as it ships today. (2) Or press **Start a draft from this version** in a row. The new draft is a change to the same process and holds the same steps, forks and checks as that version, against the process as it ships today. This is how a changed copy of a version that has left Draft is made. Either way nothing runs differently.
- **Operator — fill:** in the pop-up, **Process** (`flow`) — the list offers only a process a command can write through, with an act a person takes on a screen, each shown by its guide title; and **Title** (`title`) — what the change is for, in a few words; it cannot be blank. **Start a draft from this version** asks nothing: it sends the row's own process, the title *"{title} (copy)"* and the row's id (`fromVersion`, optional in the payload). The id, the label, the shipped version the change is drafted against and who drafted it are never fields.
- **Tester — expected state:** Draft
- **Tester — confirm:** from the pop-up: toast *"Version {label} of {process} created as a draft."*; the pop-up closes; a new row in the table on the **Changes** tab with **Version** (`<shipped version>.<n>`), **Process**, **Title**, **State** *Draft*, **Adds** *0 elements*, **Drafted by** (the sample person the seat is acting as), **Drafted** and **Actions**. The line *"No change has been drafted yet."* is gone. From a row: toast *"Version {label} created as a draft, from version {from}."*; a new row with its own label (the next number of that process), the title *"{title} (copy)"*, the same **Adds** count as the source, and **Drafted by** the person acting now. Opened in the composer, it shows the same steps and no warning is ticked. In both cases the version is in `localStorage` under `paragon.flowVersions` and is still listed after a reload. A new draft changes nothing a process does.
- **Tester — trigger event:** `t_flowversion_create`
- **Checks that can refuse:** `flowversion_author_named` — the seat must name a person (`FLOWVERSION_AUTHOR_UNATTRIBUTED`). Above **Create draft** the pop-up says which seat this is: *"This seat names nobody, so this act will be refused. Adopt a sample user on the identity panel first."*, or *"This will be recorded against {person}."* once a sample user is adopted. The button stays live; pressed from a seat that names nobody, the toast reads *"Refused: this seat names nobody, and this act is recorded against the person who takes it. Adopt a sample user on the identity panel, then take it again."* The row action shows no line before the act; the same toast is its refusal. `flowversion_process_writable` — checked in this order: the process must be registered (`FLOWVERSION_PROCESS_UNKNOWN`); it must not be one of the builder's own processes, `flowVersion` or `processStep` (`FLOWVERSION_PROCESS_SELF`, toast *"Refused: a change cannot be drafted against the process by which processes are changed."*); a command must be able to write through it (`FLOWVERSION_PROCESS_NOT_WRITABLE`); the title must not be blank (`FLOWVERSION_TITLE_BLANK`, toast *"Refused: a change needs a title, so it can be found again."*); and, when `fromVersion` is given, it must be a version this browser holds (`FLOWVERSION_SOURCE_UNKNOWN`, toast *"Refused: this browser does not hold the version the draft was to start from."*) and a change to the same process (`FLOWVERSION_SOURCE_OTHER_PROCESS`, toast *"Refused: a draft starts from a version of the same process."*). A title left empty is refused earlier, by the dispatcher, as `MISSING_FIELDS:title`. On any refusal the pop-up stays open and nothing is created.
- **Glossary:** `ROLE_NOT_PERMITTED` · `MISSING_FIELDS` · `ACTOR_IN_PAYLOAD` · `POLICY_REJECTED` · `SCOPE_DENIED` · `NO_PERSON_IN_SESSION`
- **Honesty:** the pop-up says before the act where the draft lives — *"The draft is saved in this browser and survives a reload — local to this browser, not shared, not on a server."* — and what it does: *"It is created as an empty draft against the process as it ships today; nothing runs differently."* A draft made in the pop-up is empty until it is composed and saved. A draft started from a version carries that version's elements as they are, including any that break a rule, and is checked like every other version when the list is read. Nothing else of the source travels: the new draft has its own label, no acknowledged warning, its own author and no history, and it does not record which version it started from. The **Drafted** date is the portal's declared present, not the wall clock. The form cannot name an unregistered or unwritable process, or a process of the builder itself, and the row action cannot name a version this browser does not hold or a version of another process; the act refuses each anyway.

### t_flowversion_save — Save draft <!-- transition:t_flowversion_save -->

- **Step kind:** records a fact (state-preserving)
- **Role:** buyer · compliance (atom `flow:draft`; Admin and Super Admin hold it too)
- **From → to:** Draft → same state
- **Operator — where:** `/buyer/process-flows` → tab **Changes** → in the draft's row, column **Actions** → **Compose** → the full-screen pop-up **Version {label} · {process}** (the composer) → **Save draft**. **Compose** stands on a Draft row only, and only for a seat that holds `flow:draft`. The composer is a dialog: Escape, the close button, a click outside or **Close** closes it, and each asks first when there is unsaved work.
- **Operator — do:** pick the act the step must come before, in **Act** or on the diagram of the process. Under **Add a step** choose **Approval**, **Confirmation** or **Data capture**, then press **Add {kind}**. The step is added last under **In front of “{act}”** and its form opens. Fill the form. Use the arrows on a step's row to move it earlier or later, and the bin to remove it. Read **What the rules say about this draft**; it answers as you type. For a warning that is meant, tick **Acknowledged: this is meant**. Press **Save draft**. Saving replaces everything the draft says with what is on the screen, and keeps which warnings are ticked. It decides nothing: the draft stays a draft. **Save draft** is live only while there are unsaved changes. Once everything is saved, **Propose for review** beside it is live; it closes the composer and opens the review on the question to propose. Closing with unsaved work asks *"Version {label} has changes that are not saved. Close and lose them?"*, with **Keep editing** and **Discard changes**.
- **Operator — fill:** per step: **Lane that completes it** (one buyer-side lane); **Label — English** and **Label — Indonesian**; **Instruction — English** and **Instruction — Indonesian** (what the lane is asked to do; roles only, never a person). For **Data capture**, under **Fields the lane fills in**: **Add field**, then **Field name**, the field's label in English and in Indonesian, **Type** (Text, Number, Quantity, Money, Date, Yes / no, One of a list) and **Required**. Under **Keeping people apart**: **A different person from whoever completed “{step}”** — offered for each step that comes earlier in front of the same act — and **Whoever completes this step may not then take the act**. The payload is `content` (required: the whole list of steps, forks and checks, with the process and the shipped version, which a save cannot change) and `acknowledged` (optional: a list of `<rule code>:<element>`).
- **Tester — expected state:** Draft
- **Tester — confirm:** toast *"Version {label} saved as a draft."*; the composer stays open and the line beside the buttons changes from *"Unsaved changes."* to *"Everything is saved."*. On the **Changes** tab the row's **Adds** count reads the number of steps, forks and checks saved. The record carries who saved it and when (`savedBy`, `savedAt`) and the ticked warnings (`acknowledged`); the label, the id and who drafted it do not change. After a reload, **Compose** opens on what was saved, ticks included. A draft saved with an error is listed under **Some changes no longer obey the rules of their process** with its rule code and the step's id.
- **Tester — trigger event:** `t_flowversion_save`
- **Checks that can refuse:** the act is legal in Draft only: a save sent for a version in any other state is refused by the dispatcher as `ILLEGAL_TRANSITION`, and the store writes a draft only. `flowversion_author_named` — the seat must name a person (`FLOWVERSION_AUTHOR_UNATTRIBUTED`). Beside **Save draft** the composer shows the same line as the pop-up that creates a draft: *"This seat names nobody, so this act will be refused. Adopt a sample user on the identity panel first."*, or *"This will be recorded against {person}."*. Pressed from a seat that names nobody, the toast reads *"Refused: this seat names nobody, and this act is recorded against the person who takes it. Adopt a sample user on the identity panel, then take it again."* and nothing is written. `flowversion_content_well_formed` — checked in this order: the content must be a list of steps, forks and checks (`FLOWVERSION_CONTENT_MALFORMED`, toast *"Refused: what was saved is not a list of steps, forks and checks."*); it must stay about the process and the shipped version the change was created against (`FLOWVERSION_CONTENT_MOVED`, toast *"Refused: a change stays about the process and the shipped version it was created against."*); and `acknowledged`, when given, must be a list in which every entry names a rule and what it is about (`FLOWVERSION_ACKNOWLEDGED_MALFORMED`, toast *"Refused: an acknowledgement names a rule and what it is about."*). A payload with no `content` is refused earlier, by the dispatcher, as `MISSING_FIELDS:content`. An id that is not a version in this browser is `NOT_FOUND`. The composer cannot send any of the three malformed shapes; a hand-crafted payload can. The rules R01–R19 do **not** refuse a save: a draft is allowed to be unfinished. They refuse the proposal.
- **Glossary:** `ROLE_NOT_PERMITTED` · `NOT_FOUND` · `ILLEGAL_TRANSITION` · `MISSING_FIELDS` · `ACTOR_IN_PAYLOAD` · `POLICY_REJECTED` · `SCOPE_DENIED` · `NO_PERSON_IN_SESSION`
- **Honesty:** the composer says at its foot *"A saved draft is kept in this browser. It changes no process: a change is in force only after it is approved and activated."* The save is the composer's only write. **Compose** is offered on a Draft row only; a save sent for a version that has left Draft is refused anyway. A new step is born with no lane, no label and no instruction, so the rules report it at once (R06, R07) until it is filled in. A draft saved with an error — a step with a label in only one language, for example — is kept and named under **Some changes no longer obey the rules of their process**: reported, not refused and not dropped. A name of a person in a label or an instruction is a finding (R07), not a refusal at the save. The composer and the **Changes** tab check for the same names: the ones a reader sees for the sample persons, in both languages, and their ids. The composer sends only the ticks of warnings the draft still raises, so an acknowledgement of a warning that has gone is not kept. Only the three kinds of step can be composed. The **Catalogue** tab never draws a draft's steps; inside the composer the diagram marks each act that has something in front of it with *"{n} added"*.

## 4 · Decision forks and exception paths

- **Seat holds `flow:draft` or not (before the act).** Branch A — the seat holds it: **New change** stands in the header of the **Changes** tab, and each row carries **Review**, **Start a draft from this version** and, on a Draft row, **Compose** under **Actions**. Branch B — it does not: the header reads **Changing a process is a Compliance action** with *Awaiting Compliance*, there is no pop-up, and a row offers that seat **Review** only. The tab itself, the list and the rules are readable by every seat.
- **Seat holds the act's permission or not (in the review).** Branch A — the seat holds it: the act is a button in the footer of the review. Branch B — it does not: the act's name stands there with a hand-off notice naming the lane that holds it. The review itself is readable by every seat.
- **Closing the composer with unsaved work (in the composer).** Branch A — **Keep editing**: back to the draft, nothing lost. Branch B — **Discard changes**: the composer closes and what was composed since the last save is gone. With nothing unsaved the composer closes without asking.
- **Empty draft or a draft from a version (at creation).** Branch A — **New change**: an empty draft of the process chosen. Branch B — **Start a draft from this version**: a draft of the same process with the same elements, its own label and no acknowledged warning. Branch B is the only way to change what a version says once it has left Draft.
- **Approve, return, reject or withdraw (at In Review).** Branch A — `t_flowversion_approve` — **When:** the change is right and the approver is not the proposer. Branch B — `t_flowversion_return` — **When:** it needs more work. Branch C — `t_flowversion_reject` — **When:** it is not wanted; the change ends. Branch D — `t_flowversion_withdraw` — **When:** the author takes it back.
- **Activate or withdraw (at Approved).** Branch A — `t_flowversion_activate` — **When:** the change should be in force now. Branch B — `t_flowversion_withdraw` — **When:** it should be worked on again first.
- **Retire or be replaced (at Active).** Branch A — `t_flowversion_retire` — **When:** the process should run on the shipped default. Branch B — `t_flowversion_supersede` — **When:** another version of the same process is activated or restored; the platform fires it.
- **Seat names no person (exception).** Creating, saving, proposing and withdrawing are refused with `POLICY_REJECTED:flowversion_author_named` (`FLOWVERSION_AUTHOR_UNATTRIBUTED`). Returning, approving, rejecting, activating, retiring and restoring are refused with `POLICY_REJECTED:flowversion_decider_named` (`FLOWVERSION_DECIDER_UNATTRIBUTED`). Nothing is written. Adopt a sample user on the identity panel, then take the act again.
- **No reason, or a blank one (exception).** Every act from proposing onward needs `reason`. Left out, the dispatcher refuses it as `MISSING_FIELDS:reason`. Only spaces, it is refused as `FLOWVERSION_REASON_BLANK`.
- **A change that cannot be proposed (exception).** It adds nothing (`FLOWVERSION_EMPTY`); it holds a fork, a check or a scan (`FLOWVERSION_ELEMENT_NOT_BUILT`); its process moved since it was written (`FLOWVERSION_BASE_MOVED`); it breaks a rule (`FLOWVERSION_BREAKS_RULE`); or it carries a warning nobody acknowledged (`FLOWVERSION_WARNING_UNACKNOWLEDGED`). The first four are asked again at approval, at activation and at restore.
- **The approver is the proposer (exception).** Refused as `FLOWVERSION_APPROVER_IS_PROPOSER`. A Super Admin passes with a recorded one-line reason; an Admin is refused. Rejecting, returning and retiring have no such rule.
- **A sample person on production (exception).** Approving, activating and restoring are refused as `FLOWVERSION_SAMPLE_IN_PRODUCTION`. On a demo or preview deployment a sample person may take them.
- **A version in force that no longer obeys the rules (derived, not an act).** It is set aside, by name: the version stays `Active` on the record, the process runs on the shipped default, and no step of it is due. The **Changes** tab names it in a warning, and the **Catalogue** tab says on the process that it was set aside. Retire it, or start a draft from it.
- **An act of a process whose version in force adds a step (derived, not an act).** The act is refused as `STEP_PENDING`, naming the step, until the step's lane completes it. When the act succeeds, the completions in front of it are used up, so a document that comes round to the same act meets the step again.
- **Blank or missing title (exception).** A title of spaces only is refused by `flowversion_process_writable` (`FLOWVERSION_TITLE_BLANK`). A title left empty is refused by the dispatcher as `MISSING_FIELDS:title`, before any check runs.
- **Process that cannot be changed (exception).** A process the platform does not have (`FLOWVERSION_PROCESS_UNKNOWN`) or one no command can write through (`FLOWVERSION_PROCESS_NOT_WRITABLE`). The form offers neither; a hand-crafted payload naming one is refused.
- **A change to the builder's own processes (exception).** A payload naming `flowVersion` or `processStep` is refused (`FLOWVERSION_PROCESS_SELF`): a step in front of an act on a change, or in front of completing a step, would let the builder gate itself. The **Process** list does not offer them; the act refuses them anyway.
- **A source that cannot be started from (exception).** A `fromVersion` this browser does not hold is refused (`FLOWVERSION_SOURCE_UNKNOWN`); one that is a change to another process is refused (`FLOWVERSION_SOURCE_OTHER_PROCESS`). The row action sends the row's own id and process, so only a hand-crafted payload meets either.
- **Payload that names who acted, or an id or label (exception).** A payload carrying a key the platform keeps for the person acting is refused by the dispatcher (`ACTOR_IN_PAYLOAD`). An id or a label in a payload is ignored: the store assigns both.
- **Save that is not a change, or moves it (exception).** Content that is not a list of steps, forks and checks is refused (`FLOWVERSION_CONTENT_MALFORMED`); content naming another process, or another shipped version, is refused (`FLOWVERSION_CONTENT_MOVED`); an `acknowledged` that is not a list of `<rule code>:<element>` is refused (`FLOWVERSION_ACKNOWLEDGED_MALFORMED`). The composer sends none of these. A save for a version that has left Draft is `ILLEGAL_TRANSITION`.
- **An act a step cannot stand in front of (in the composer).** **Act** offers only an act a person takes on a screen. Every other act of the process is listed under **Acts a step cannot stand in front of** with its reason: *"a system fires it, not a person"*, *"another act fires it"*, *"it creates the document, so there is no document yet for a step to be due on"* or *"no screen offers it"*.
- **A finding in the composer (derived, not an act).** An error, a warning or information is shown as the draft is written. None of them stops **Save draft**. A warning carries the tick **Acknowledged: this is meant**; the tick is kept with the save and is what the proposal reads.
- **A version that no longer obeys its rules (derived, not an act).** Each time the list is read, every stored version is checked against the rules as they are now. One that breaks a rule of kind *Error* is kept, listed, and named with the rule it breaks. A draft saved unfinished is named there too. Nothing is removed.
- **A stored row that is not a version (derived, not an act).** A row whose id, label, state, title, stamps or history do not hold together is refused when it is read, named with its reason, and still kept in storage. A row whose state is not where its history leaves it is refused the same way. Its id and its label are not given out again.

## 7 · Status history

Every dispatch writes one `TransitionEvent`: `event` = the transition id, `actor` = `buyer:all` (the seat, not a person), `ts`, `outcome`, one `correlationId` per command, and `flowVersion` — which version of the process the act was taken under. A separate `attribution` field records who could be named. Refusals are written too, with their reason. The version itself carries `createdBy` and `createdAt`, and `savedBy` and `savedAt` once it has been saved; each save replaces the last. From proposing onward the version keeps its own `history`: one line per act, oldest first, never rewritten. It is kept on the record because the record is what survives a reload. The review shows it under **History**, oldest first, each act with who took it and the reason.

Worked sequence, as testers holding Compliance would produce it in a browser with no versions yet, on a demo or preview deployment. From T+2 on, each act on the version is taken in the review, with a reason:

| Time | From → to | Actor (role) | Trigger | Event |
|---|---|---|---|---|
| T+0 | ∅ (refused) | buyer · compliance, seat names nobody | **New change** → choose a process, write a title → **Create draft** | `t_flowversion_create`, `outcome: failed`, `POLICY_REJECTED:flowversion_author_named` |
| T+1 | ∅ → Draft | buyer · compliance, acting as a sample user | the same, after adopting a sample user on the identity panel | `t_flowversion_create` — version `fv-1`, label `<shipped version>.1` |
| T+2 | Draft (refused) | buyer · compliance, the same person | propose the empty draft, with a reason | `t_flowversion_propose`, `outcome: failed`, `POLICY_REJECTED:flowversion_obeys_rules` (`FLOWVERSION_EMPTY`) |
| T+3 | Draft → Draft | buyer · compliance, the same person | **Compose** → pick an act → **Add Approval** → choose the lane, write both labels and both instructions → **Save draft** | `t_flowversion_save` |
| T+4 | Draft → In Review | buyer · compliance, the same person | propose, with a reason | `t_flowversion_propose` |
| T+5 | In Review (refused) | buyer · compliance, the same person | approve, with a reason | `t_flowversion_approve`, `outcome: failed`, `POLICY_REJECTED:flowversion_approver_not_proposer` (`FLOWVERSION_APPROVER_IS_PROPOSER`) |
| T+6 | In Review → Approved | buyer · compliance, a second sample person | approve, with a reason | `t_flowversion_approve` |
| T+7 | Approved → Active | buyer · compliance, either person | activate, with a reason | `t_flowversion_activate` |
| T+8 | (the gated process) | the lane that holds the gated act | take the act the step stands in front of | that act, `outcome: failed`, `STEP_PENDING` naming the step; the document does not move |
| T+9 | Active → Retired | buyer · compliance, a named person | retire, with a reason | `t_flowversion_retire`; the gated act is no longer refused for the step |
| T+10 | Retired → Active | buyer · compliance, a named person | restore, with a reason | `t_flowversion_restore` |

A second version of the same process activated while `fv-1` is in force would add one more event, fired by the platform: `t_flowversion_supersede` on `fv-1`, Active → Retired.
