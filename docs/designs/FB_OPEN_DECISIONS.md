# Flow Builder — decisions for the operator

**Seat 3, consultant, Ops Project #11 · 2026-10-12.** Each has a recommendation. Decisions 1 to 4 shape the build and are needed before FB-1; the others are needed before the batch named. Section numbers refer to `DESIGN_6_v2.md`.

| # | Decision | Recommendation | Needed by |
|---|---|---|---|
| **1** | **What a runtime change may be.** Additions only (steps, checks and forks in front of existing acts), or also changes to the shape of a process (a new stored state, a re-routed or removed act, a removed check). | **Additions only at runtime.** It is what makes "an active version can never remove a refusal" true, and it is what requirement 1 asks for. A new stored state would be unknown to the pages (280 comparisons against a state literal in 53 surface files) and to the command targets (37 branches on the destination state). Shape changes stay generated, reviewed code, which is SE work. This also confirms that Design 6's "no runtime override" is reversed for additions. | FB-1 |
| **2** | **Documents in flight.** An act taken after activation obeys the version in force at that moment, or a document keeps the version it was created under (the earlier ruling). | **The version in force when the act is taken**, with every event and step row saying which version that was. The earlier ruling protected documents from a renamed or removed state, which an additive version cannot cause. A control should apply from the moment it is switched on, and it can then be seen on the sample documents; several processes cannot create a new document in the fixture at all. §6.4. | FB-4 |
| **3** | **Who holds the three rights** (draft and propose; approve, reject and return; activate, retire and restore). | **Compliance**, beside the rights to grant roles and switch modules. Admin and Super Admin hold them as well, because their bundles are the union of the others. Four eyes separates persons, not lanes. If the process owner's own lane should be able to propose, give `flow:draft` to that lane later; approval stays with Compliance. | FB-1 |
| **4** | **Where it lives.** Two views on the Process Flows page (Catalogue, Changes), or a route of its own under Platform. | **On the Process Flows page**, as ruled for Design 6: one page, no new route, no second rendering of the catalogue. §8. | FB-1 |
| **5** | **Sample persons.** May a sample person approve and activate a change? | **Yes on demo and preview deployments, marked `(SAMPLE)`; refused on production** — the rule module switching already follows. Design 6's "never a sample person" would make the builder impossible to demonstrate before sign-in exists. | FB-3 |
| **6** | **Approve and activate: one act or two.** | **Two.** Approving says the change is right; activating says it is in force now. Two acts allow approval ahead of the start day and make rollback the same switch thrown back. Activation needs a named person and a reason, not a second pair of eyes. | FB-3 |
| **7** | **Rollback.** Who may return a process to the shipped default, and does restoring an earlier version need a new approval? | **Any one named holder of the activate right, with a reason, for both.** Returning to the default is the safe direction and should never wait for a second person. An earlier version was already approved under four eyes; it is validated again at restore, and refused if the shipped process has moved. | FB-6 |
| **8** | **How far the Super Admin exemption reaches** in the builder. | **The two person-separation checks only** (approver is proposer; a step's separation rule), each with the one-line reason, recorded and shown on the activity view. Not a validation error, not a moved base, not a pending step: those are not four-eyes checks. | FB-3 |
| **9** | **Supplier-side steps.** May a step be given to a supplier lane? | **Not in the first build.** Buyer-side lanes only; a buyer-side step may still stand in front of an act a supplier takes. Supplier-side steps need a second pair of acts scoped to the owning supplier, which is batch FB-7 if wanted. | FB-5 |
| **10** | **What a scan is.** | **A code typed or wedge-scanned into a field, which must equal a named field of the document** (its number, a material code, a batch). It works in a browser today. Camera or device scanning is SE work. | FB-5 |
| **11** | **Where versions are kept until the backend exists.** In the browser across reloads (as custom roles are), or for the session only (as module switches are). | **In the browser, across reloads**, with a notice that they are not shared between people or devices. A change that vanishes on reload would look like a defect. Documents and step records still reset on reload, as they do today, and the page says so. | FB-1 |
| **12** | **Steps in front of acts that refuse, cancel or withdraw.** Allowed, warned, or forbidden. | **Allowed with a warning the proposer must acknowledge**, and the same for a change that leaves a state with no way out except through an added step (rules R15, R16). A legitimate control on a cancellation exists; it should be chosen knowingly. If a hard ban is wanted, it needs a ruled list of protected acts. | FB-1 |
| **13** | **Conditions on dates.** | **Not offered in the first build.** A step that a date decides is a clock-fired rule, which the platform forbids. If wanted later, it compares against the declared present, like every other deadline. | FB-5 |

## Two things to know that are not decisions

- **The handover set says the opposite today.** D1 lists the Flow Builder as SE-16 "not built", the decision register records "no runtime override", and D3 says "flows are code". They are corrected in batch FB-6, or earlier if the operator prefers the set to be right from the first merge.
- **The first build cannot reuse an existing check on another act.** The 153 checks each read the shape of their own document. The builder offers three generic rules instead (a named person, a value, a different person). Reuse can be opened per check later, with a description of what each one reads.
