## 2 · The command spine

Everything that changes state is a **command**: `{ transitionId, entity, entityId, payload, expectedState?, idempotencyKey?, decision? }` (`CommandInput`, `src/services/data/types.ts`). It goes through one function, the **dispatcher** (`src/services/transitions/dispatcher.ts`, built by `createDispatcher`), and returns a result; it never throws for a business refusal.

### 2.1 Flows and transitions

A **flow** is a state machine for one entity type: `{ entity, states, initial, terminals, transitions, version }` (`FlowDefinition`, `src/services/transitions/schema.ts`). A **transition** ("verb") is an edge: `id` (always `t_<entity>_<verb>`), `from`, `to` (or `statePreserving: true` for a verb that appends a record without moving state), `trigger` (`user` | `system` | `cascade` | `creation`; a `clock` trigger is refused at the type level, law 0.5), `requiredRole` (one permission atom, §3), `requiredFields`, `policyHooks`, and `surfaceable` (whether a screen is intended at all, and if not, who owns the fact). Flows live in `src/services/transitions/flows/*.flow.ts` and self-register on import (`src/services/transitions/index.ts`); `getKnownFlows()` is the only honest way to count them (33 at the pin, pinned by C1; v2's pin: 30. *The file at the v2 tag said 29 here, which was stale at its own pin.*). `validate.ts` rejects a flow whose declared terminals have exits or whose exit-less states are undeclared; `flowGraph.test.ts` holds the catalogue against the loose-end census (`looseEndCensus.ts`), which lists holes that ship deliberately and can only shrink.

### 2.2 CommandTargets

A flow can exist without being writable. A **CommandTarget** is the per-entity adapter the dispatcher writes through: `readState`, `readScopeOwner`, `readEntity`, `applyTransition`, and for creation verbs `creationOwner?`, `requireCreationOwner?`, `create?(payload, toState, scope, decision?)` (C1 Axis 3). All wired targets are in the `TARGETS` map in `src/services/data/mock/MockCommandService.ts`; `WIRED_COMMAND_TARGETS` is the exported census (27, pinned by C1; v2's pin: 24. *The file at the v2 tag said 23 here, stale at its own pin.* `flowVersion` was added at FB-1, `processStep` at FB-3 + FB-4 and `masterDataRequest` at MD-4 + MD-5). Since FB-3 + FB-4 `applyTransition` takes a sixth, optional argument, `bypass`: the checks that stood aside for a Super Admin on this act, with the reason (C1). Since RFx-2 (#408) the dispatcher tells a target which verb it is applying, and the RFQ target writes each guarded field (an awardee, a rate, an advance, a conclude reason) only for its own verb; before that a guarded key on any RFQ verb was written by payload shape (`src/services/data/mock/rfx2StorePayload.test.ts` reproduces the defect). The unwired set is `compliance`, `contract`, `goodsReceiptLine`, `invoiceMatch`, `obligation`, `shipment`.

### 2.3 The dispatcher's order of refusals

`COMMAND_REFUSALS` (`src/services/transitions/refusals.ts`; thirteen members at the pin, twelve in v2) is order-pinned to the dispatcher's construction sequence, and a test asserts the order:

```
UNKNOWN_TRANSITION → UNKNOWN_ENTITY → MISSING_ENTITY_ID → MODULE_INACTIVE
→ ROLE_NOT_PERMITTED → STALE_STATE → ILLEGAL_TRANSITION → ACTOR_IN_PAYLOAD
→ MISSING_FIELDS → STEP_PENDING → UNBOUND_HOOK → POLICY_REJECTED → UNSUPPORTED_CREATION
```

- **`MODULE_INACTIVE`** (PR #388): the module gate (`moduleActivationTarget.ts`, `moduleGate`) refuses a verb whose side, module or part is switched off; the detail names it (`SHP`, `GRC.qualityHold`, `side:supplier`). It runs after the thrown tenancy pair (`SCOPE_DENIED` / `NOT_FOUND`) and before role.
- **Role before state:** a caller without the atom learns nothing about the document.
- **`STALE_STATE`** is the optional compare-and-set on `expectedState`, checked before legality so a stale caller is told why. It is not a content-revision check.
- **Tenancy:** the supplier arm compares `readScopeOwner()` to `scope.supplierId` unconditionally, so a target that returns `null` denies every supplier (`ownerlessScope.test.ts`).
- **`ACTOR_IN_PAYLOAD`** refuses any payload key declared as attribution (`src/services/identity/attributionKeys.ts`); who acted comes from the session, never the payload (C10 Amendment 1).
- **`idempotencyKey`** is a per-tenant replay guard: a redelivery returns the first result. The intake cascade uses the intake line id as its key, which is one of the two reasons one line raises at most one requisition (`intakeCommitIdempotency.test.ts`).
- **`STEP_PENDING`** (PR #438): a step that the version in force added is due in front of the act. The detail is `<process>:<document>:<step>`, with `:declined` after it when the latest decision on the step was a decline. It is raised only by a dispatcher that was given a `flowOverlay` (§2.7).
- **`bypassReason`** (ADM-1, #420; a command field, not a refusal kind): when a check stood aside for a Super Admin seat the command must carry `CommandInput.bypassReason`, one line of 1 to 300 characters, or it is refused `POLICY_REJECTED:super_admin_bypass_reasoned:SUPER_ADMIN_REASON_REQUIRED` with nothing applied. From any other seat the field is ignored. The dispatcher's read-only `bypassRulesFor` previews which checks would stand aside, so a reasoned act leaves one event, not a refusal followed by an act.

### 2.4 Policy hooks

A transition names hooks by key in `policyHooks: [...]`; keys are members of `POLICY_HOOKS` (`src/services/transitions/policyHooks.ts`) and implementations are bound in `src/services/transitions/policies.ts`. A hook receives `{ entityId, currentState, toState, payload, target, scope }` and reads the document through `target.readEntity`, never by importing a store. A named hook with no binding refuses `UNBOUND_HOOK`. Families added since v1: `INTAKE_ONE_GRAIN` (one material × period commits at most once across grains, PLN-2); the RFQ hooks (a named person to publish, cancel, award, advance or conclude, `RFQ_ACTOR_UNATTRIBUTED`; `PUBLISH_DEADLINE_PAST`; `AWARD_FX_UNPINNED`; `SHORTLIST_UNDER_FLOOR`; the questionnaire, criteria and score-sheet checks); four on `t_quotation_submit` (`QUOTE_EVENT_NOT_OPEN`, `QUOTE_DEADLINE_PASSED`, `QUOTE_ALREADY_SUBMITTED`, `QUOTE_VALIDITY_PAST`); and two on payment release (`INVOICE_RELEASER_IS_APPROVER`, `INVOICE_RELEASER_UNNAMED`). The refusal names are taken from PRs #396 and #405–#410; the guides `rfq`, `quotation`, `stageResponse` and `invoice` list each with its meaning. Added since v2: the Super Admin exemption — a hook asks the dispatcher `exempt(head)` at the point it would refuse, and five refusal heads stand aside for a named `super_admin` seat (`INVOICE_RELEASER_IS_APPROVER`, `PSL_DECIDER_IS_PROPOSER`, `PSL_SEAT_HOLDS_BOTH_AUTHORITIES`, `MATERIALREQUEST_DECIDER_IS_REQUESTER`, `SAMPLE_ACTOR_CANNOT_LOOSEN`), joined at FB-3 + FB-4 by `FLOWVERSION_APPROVER_IS_PROPOSER` and the two step separations (`STEP_COMPLETER_IS_EARLIER_COMPLETER`, `STEP_COMPLETER_MAY_NOT_ACT`); derive the set from the `exempt?.(` calls in `policies.ts`, which `adm1SuperAdmin.test.ts` holds equal to the labelled one. Also added at ADM-1: the hook `gr_receiver_named` on `t_gr_create` (refusal `GR_RECEIVER_UNATTRIBUTED`), and two new refusals, `INVOICE_LINES_REQUIRED` and `INVOICE_LINE_EXCEEDS_CONFIRMED`, raised on `t_invoice_create` by the existing hook `invoice_lines_within_received`. Added at the Flow Builder: the `flowversion_*` hooks (author and decider named, process writable, content well formed, obeys the rules, approver is not the proposer, not a sample person in production, reason authored) and the `step_*` hooks (actor named, may be taken, fields given, decline reasoned); C1's FB notes list each refusal in order. Earlier families: `INTAKE_*` (A2), `PUB_*` (publication: one open draft per grain, firm lines, supplier collaborated, actor attributed), `MODULE_*` (nine, on `t_module_set`, including "a sample person may not switch modules in production").

### 2.5 Cascades and rollups

Some verbs fire other verbs (`src/services/transitions/cascades.ts`): `t_gr_reject` / `t_gr_partial_approve` → `t_asn_discrepancy`; `t_gr_post` → `t_invoice_match`; since OPS-1 also `t_invoice_submit` → `t_invoice_match` and `t_invoice_resolve` → `t_invoice_match` (so an invoice that arrives after its receipt is matched); `t_rfq_create` → `t_pr_source`; `t_rfq_award` → `t_quotation_award` / `t_quotation_reject`; since SRC-1 and RFx-1 `t_rfq_cancel` → `t_quotation_withdraw` and `t_rfq_conclude` → `t_quotation_withdraw`; `t_intake_commit` → `t_pr_create`; `t_requirementresponse_promote` → `t_requirementresponse_supersede`; `t_publication_publish` → `t_publication_supersede`; since FB-3 + FB-4 `t_flowversion_activate` and `t_flowversion_restore` each → `t_flowversion_supersede` on every other `Active` version of the same process, so at most one is in force (atom `flow:supersede`, an automation atom). The fan-out runs under an `automation` grant (`AUTOMATION_ATOMS`) and re-dispatches inside a `catch {}`, so it is the one path where a narrowed grant deletes an act silently. The goods-receipt header verb is derived, not chosen (`grRollup.ts`); a grep for a literal transition id will miss it. Resolve non-literal ids before concluding a verb is dead.

### 2.6 The SAP boundary (Option B)

Two verbs, `t_gr_post` and `t_invoice_release_payment`, land in an interim state and `settle(correlationId)` finalises them (`settleFaults.ts`, `sapBoundary.test.ts`). The real implementation is a SAP settlement webhook (C5, SE-6). No source may construct a governed document number (`PO-`, `GR-`, `INV-`, `CTR-`, `SA-`) outside the mock backend: `src/lib/documentNumberGate/documentNumberGate.test.ts` (C11 V15, PR #392).

### 2.7 The process-change overlay (new in v3; PRs #433, #435, #438)

A **version** is a document that lists additions to one process that already runs (`src/services/flowBuilder/flowVersion.ts`): steps in front of an existing act. It has no field that could name a state, move a lane, or drop a check or a required field, so **an active version can add a refusal and can never remove one** (`validateVersion.test.ts` holds that over the real catalogue). No flow-builder module calls `flowRegistry.register`; the shipped catalogue stays what the code declares.

- **The machine.** `flowVersion.flow.ts`: `Draft → In Review → Approved → Active → Retired`, or `Rejected` (the one ending). Eleven acts. Content is written in `Draft` only. Every act a person takes needs a named person (create and save included), and from proposing on a reason as well; the one act no person takes is the cascade `t_flowversion_supersede`. Approving and activating are two acts. Atoms: `flow:draft` (create, save, propose, withdraw), `flow:decide` (return, approve, reject), `flow:activate` (activate, retire, restore); all three are `compliance` atoms. `t_flowversion_supersede` requires `flow:supersede`, an automation atom.
- **The rules.** One pure library, `validateVersion(content, world)`, handed its world by `liveWorld`. Rules R01–R08 and R12–R19 exist (`VERSION_RULES` in `validateVersion.ts`); R09–R11 are not built. A save is not refused by the rules (an unfinished draft is kept and reported); a proposal, an approval, an activation and a restore each run them again (`flowversion_obeys_rules`). Derive the rules from `VERSION_RULES`, the acts a step may stand in front of from `isGateable` (same file), the kinds that can be composed from `COMPOSABLE_KINDS` (`src/pages-v2/process-flows/composerModel.ts`).
- **The gate.** `createDispatcher` takes ONE optional dependency, `flowOverlay` (the object is `src/services/flowBuilder/flowOverlay.ts`; `MockCommandService.ts` injects it). Absent, nothing changes — every pre-existing caller is untouched. Present, the dispatcher asks what the version in force adds in front of the act: it refuses `STEP_PENDING` while a step is due; after the shipped hooks it may refuse once more as `POLICY_REJECTED:added_check:STEP_COMPLETER_MAY_NOT_ACT`; on success the completions in front of the act are spent; and it stamps every event about a registered transition with `flowVersion`.
- **The step ledger.** `processStep.flow.ts` is a ledger flow (one state, `Recorded`; no creation verb). The entity id is `<process>:<document>:<step>`. `t_step_complete` and `t_step_decline` append a row (`processStepTarget.ts` → `stepLedger.append`). Every buyer-side lane holds `step:complete`; which lane may take a given step is the step's own `lane`, decided by ONE function, `stepOpenFor` (`stepsDue.ts`), that the check and the surface both call. What is due on a document is `dueStepsFor` (`stepsDue.ts`, the read half, with the world handed in so a supplier page's imports never reach the command service).
- **Rollback.** `t_flowversion_retire` returns the process to the shipped default; `t_flowversion_restore` brings an earlier version back and validates it again. An active version that no longer obeys the rules — typically because its process moved (rule R02) — is set aside by name and the process runs as shipped (`inForce` in `stepsDue.ts`).
- **Where it lives.** Versions: `localStorage['paragon.flowVersions']` (`flowVersionStore.ts`), per browser, re-validated on read. Step records: in memory (`stepLedger.ts`), lost on reload with the documents. Surfaces: `src/pages-v2/process-flows/` (`ChangesView`, `ChangeComposer`, `ChangeReview`) and, on the processes named in `STEP_SURFACES` (`stepSurfaces.ts`), the shared `NextActLine` with the step line `DueStepLine` (`src/components/v2-features/`).
- **Boot seeds.** The sample-data seeds dispatch real commands at start-up. With a change in force they would be stopped by its added step, so the overlay stands down while the boot seeds run and at no other time: the switch is `fixtureSeeding(on)` in `stepsDue.ts`; `src/main.tsx` turns it on before the first boot seed and off after the last, and `src/services/data/mock/fb4Overlay.test.ts` scans the source to hold that no other file calls it (PR #438). While it is on, an event carries the shipped version. A server-side seed needs the same decision.
- **What cannot be done at runtime.** A new state, a re-routed or removed act, a different lane or required field on an existing act, a new document type. Those are code (`docs/designs/DESIGN_6_FLOW_BUILDER.md` §7). Forks, checks and scans cannot be put in force yet: a version holding one is refused at proposal (`FLOWVERSION_ELEMENT_NOT_BUILT`).

### 2.8 The master-data replica and the change request (new at the re-pin; PRs #434, #436, #437, #439)

SAP S/4HANA owns master data. The portal holds a **replica** it reads (`src/services/masterData/`: `replicaStore.ts`, `seed.ts`, `lookup.ts`, `materialMasterView.ts`; the read seam is `IMasterDataService`), and since #439 it **proposes** changes through one flow. C13 is the contract: §1 to §7 for the replica, §8 for the request. Two sentences hold everywhere: **the only code that writes a replica record is the sync applier** (`applySyncRun`, `syncApplier.ts`), and **no act of the request flow writes a master record**.

- **The machine.** `masterDataRequest.flow.ts`: `Proposed → In Review → Approved → Sent to SAP → Completed in SAP` or `Declined by SAP`; `t_mdr_return` takes `In Review` back to `Proposed`; `Rejected` and `Withdrawn` are the other two endings. Eight states, nine acts (`t_mdr_propose`, `_start_review`, `_return`, `_approve`, `_reject`, `_withdraw`, `_hand_off`, `_sap_complete`, `_sap_decline`). Atoms: `masterdata:propose` (procurement, planning), `masterdata:review` (planning, compliance), `masterdata:handoff` and `masterdata:record-sap-answer` (procurement). Approving says the request is right; handing off says it goes now; they are two acts.
- **The rules of a proposal.** `src/services/masterData/changeRequest.ts` is the document and its rules, with no store and no dispatcher in it. Derive, do not restate: the kinds from `MDR_KINDS` (three today), the fields a kind may propose from `MDR_FIELDS` (`portalSupplierId` is the portal's pointer and is never proposed), the reviewing lane from `REVIEWER_LANE`, the open states from `MDR_OPEN_STATES`. `validateProposal` refuses by name (`MDR_KIND_UNKNOWN`, `MDR_REASON_BLANK`, `MDR_CREATE_CARRIES_KEY`, `MDR_SUBJECT_UNKNOWN`, `MDR_FIELD_NOT_PROPOSABLE`, `MDR_FIELD_MISSING`, `MDR_VALUE_NOT_IN_TABLE`, `MDR_NOTHING_CHANGES`). A create carries every field and **no key**: SAP gives the key.
- **The hooks.** `mdr_actor_named` on every act (the shared `namedSeatHook`, bound in `policies.ts`) and `mdr_approver_not_proposer` on approve and reject (also `policies.ts`; it asks the dispatcher's Super Admin exemption, `exempt('MDR_APPROVER_IS_PROPOSER')`, where it would refuse). The other five are bound where the target is made (`src/services/data/mock/masterDataRequestTarget.ts`): `mdr_proposal_valid` (the rules above, then `MDR_DUPLICATE_OPEN`), `mdr_reviewer_lane` (`MDR_WRONG_LANE`: a material request is planning's, a supplier request compliance's; a superset role passes), `mdr_base_unchanged` on approve and hand-off (`MDR_SAP_CHANGED_FIRST`), `mdr_note_authored` (`MDR_NOTE_BLANK`), `mdr_sap_answer_admissible`.
- **The base, and "SAP wins".** At proposal the store records the **base**: the sync run, the read time and the subject's value of each proposed field (`baseOf`). Before an approval and again before a hand-off, `fieldsSapChanged` compares the base with the replica as it stands; if a sync run has moved a proposed field the act is refused, and the request is withdrawn and proposed again. A change to a field the request does not touch does not hold it.
- **The target.** `readScopeOwner: () => null`, so a supplier scope is refused at scope (the document is Paragon's). `create` mints the id and the portal's own number (`mdr-0001`, `MDR-2026-0001`; never SAP's), stamps the proposer and the base, and opens the history; `applyTransition` appends one history row per act (who, when, the note).
- **Hand-off.** `handOffPackage(request)` builds what would be handed to SAP: the request number as the external reference (and the feed's idempotency key), the kind, the object, the subject key, the proposed fields, the reason, who proposed and who agreed, and the base. The page shows it. Nothing is sent: SAP is not connected, and the call to SAP MDG is SE-6.
- **SAP's answer.** `t_mdr_sap_complete` and `t_mdr_sap_decline` are `user` acts in the fixture. `mdr_sap_answer_admissible` requires SAP's request number, refuses an answer not marked as a sample (`MDR_SAP_NOT_CONNECTED`), and refuses a sample answer on production (`MDR_SAMPLE_ANSWER_IN_PRODUCTION`, read from `moduleDeployment.isProduction()`). A sample completion delivers its record **through the applier** as a run of its own (`SAMPLE-ANSWER-<request number>`, stamped `SAMPLE`); a new material arrives under a sample key (`SAMPLE-<request number>`), never one the request carried. The run id is the request number, so recording the same answer twice changes nothing the second time. The real feed fires both verbs under the automation grant (SE-6).
- **The sample sync.** `src/services/masterData/sampleSync.ts`: one prepared run (`SAMPLE-SYNC-0001`) that changes a description, adds an incoterm, blocks a supplier and carries one record the replica refuses by name. `runSampleSync()` is a function the page calls, not a verb; it returns `SAMPLE_SYNC_IN_PRODUCTION` or `SAMPLE_SYNC_ALREADY_RUN` instead of running. `replicaOneWriter.test.ts` holds the applier's callers to a named set of three (the applier's own module, the request target, the sample sync), so a fourth caller is red.
- **Surfaces.** `src/pages-v2/BuyerMasterData.tsx` with `src/pages-v2/master-data/ChangeRequests.tsx`; the views are `MASTER_DATA_VIEWS` (`masterDataView.ts`: materials, suppliers, reference, requests, sync), and `/buyer/master-data/requests` is the same page on its requests view. Every act goes through one hook, `useMasterDataRequestAct` (`src/services/query/commandHooks.ts`), which names the verb and dispatches on `ICommandService`. A refusal is rendered from its HEAD (`mdrRefusal.ts`, `MDR_REFUSAL_HEADS`, with copy under `masterData.request.refusal.*` in EN and ID), because one developer sentence names a person by id. *That file's header names a spec `mdrRefusal.test.ts`; no such file exists at the pin, and the both-ways assertion is in `src/services/data/mock/masterDataRequestCommand.test.ts` (D8 §11).*
- **Where it lives.** Requests: in memory (`src/services/data/mock/stores/masterDataRequestStore.ts`), gone on reload, and the page says so. Nothing is seeded: the store opens empty (`guides.test.ts` holds the three wired flows that are empty at seed by name).
- **What is not built** (C13 §8; PR #439): the call to SAP MDG and the feed for SAP's answer; persistence; supplier create and extend requests; folding the earlier `materialRequest` lane in; a request raised by an approved supplier application; a blocked or deletion-flagged record refusing new documents. No sample-person bar exists on this flow's own acts: a named sample person may propose, review, agree and send on any deployment (`SE_BACKLOG_v3.md` row 181).

## 3 · Atoms, lanes, seats and modules

A **permission atom** is the `requiredRole` string on a transition, `<entity>:<verb>` (for example `po:confirm`, `publication:approve`, `module:set`). There is no separate permission table: the transition IS the atom (C10 §3.3, C11 V3). `catalogRoles()` derives the vocabulary from the registry.

A **system role** is a named bundle of atoms (`SYSTEM_ROLES`, `src/services/transitions/businessRoles.ts`), built from `LANE_BUNDLES`. Fourteen at the pin (pinned by `src/handoverFigures.pin.test.ts`): `procurement`, `receiving`, `finance`, `compliance`, `planning`, `requisitioner`, `buyer`, `supplier`, `commercial`, `fulfilment`, `back_office`, `buyer_all`, `admin`, `super_admin` (thirteen at the `handover-v2` tag). `super_admin` was added at ADM-1, and `admin` no longer spans the tenancies: both administrator roles hold every buyer-side atom and no supplier-side one. `super_admin` is the one seat the four-eyes checks stand aside for, with a recorded reason (`src/services/identity/superAdmin.ts`; C1, RE-HARVEST ADM-1). `buyer` and `supplier` are zero-atom **tenancy anchors** so a custom role can be as narrow as nothing. `businessRoles.test.ts` pins both directions between the bundles and the derived atoms. Notable placements: `module:set`, `delivery:policy-set` and `role:grant` sit in `compliance` (whoever is measured by a setting may not set it); `publication:approve` (signing firm lines) sits in `procurement`; `delivery:confirm` (accepting an inferred drawdown) is a buyer act in `procurement`. Three atoms are new since v1: `intake:triage` (the planning lane commits, dismisses and restores an intake line; before PLN-3 these carried `pr:create`), `rfq:evaluate` (scoring an RFP proposal; procurement) and `stageresponse:submit` (a supplier's answer at the RFI and RFP stages), all in `LANE_BUNDLES`, `businessRoles.ts`. New since v2: `flow:draft`, `flow:decide` and `flow:activate` (compliance; changing a process), `step:complete` (every buyer-side lane; completing or declining a step a change added), and `flow:supersede`, which is an automation atom and is held by no person.

A **seat** is what a session holds: `CurrentIdentity = { personaType, supplierId, supplierName, businessRoles, actor }` (`src/context/CurrentIdentityContext.tsx`, `identitySources.ts`). `personaType` is tenancy only; authorisation comes from `businessRoles` resolved by `atomsForSeat`; a seat with no `businessRoles` is refused. The demo seat opens holding every lane on its side and can be narrowed in the identity panel. **Custom roles** are `{ parent, adds }`, additive only, persisted in `localStorage['paragon.customRoles']`, granted through the audited verb `t_role_grant`.

A **module** is a switchable slice of the platform (`src/services/modules/registry.ts`: 16 codes, `PLT` always on, all `Active` by default in `activation.ts`). The `flowVersion` and `processStep` flows and the `masterData` capability belong to `PLT`. The `masterDataRequest` flow and the route `/buyer/master-data/requests` belong to `MAT`, beside `materialRequest`: reading master data is the platform's and cannot be switched off, while proposing a change rides the Material requests module (the registry's own comment, #439). The ledger of switch acts is append-only and in memory (`moduleActivationStore.ts`; no browser storage, so a reload returns the defaults); what is in force is derived at read (`effectiveActivation`). Every route is wrapped in `<ModuleGate>` (`src/context/ModuleActivationContext.tsx`): an OFF module's pages still render, read-only, and guarded verb slots show a module-off notice before any role notice (`src/services/modules/availability.ts`).

**Cross-role handoff.** When a seat cannot fire a verb but another lane can, the surface renders a notice naming the owning lane instead of a gap (`handoff.ts`, `useVerbAvailability`, `HandoffNotice`). The unit of coverage is (surface × verb × entrance).

## 4 · The audit trail (DR-10)

Every dispatch outcome, accepted or refused, emits one `TransitionEvent` (`src/services/transitions/events.ts`): `event`, `actor` (a seat key), `scope`, `correlationId`, `causationId?`, `outcome`, `reason?`, `ts`, and five optional fields (three in v2): `bypass?` (`{ rules, reason }`, present only on an act a Super Admin seat took past a check; ADM-1), `flowVersion?` (`<entity>@<version>`, the version of the process the act was taken under, refusals included; FB-4), `decision?` (governed-decision provenance), `attribution?` (which person acted, taken from the session and set only on `user`-trigger transitions; `attributionFor` in `dispatcher.ts`; v2 cited `:431-432`, which has moved), `subject?` (`{ entity, entityId, from, to }`, added at G1). Cascaded commands share a `correlationId` and carry `causationId`; the planning grid's push uses the first dispatch's `correlationId` as the causation anchor for every row. The shipped sink is in-memory; the SE Team's durable sink persists this exact shape (C3, pinned by `c3Events.contract.test.ts`).

## 6 · The declared present

Fixtures carry dates. The tree has **one declared present**: `DECLARED_PRESENT` in `src/services/data/fixturePresent.ts`, computed as `BPJPH_MANDATE_DATE` (`2026-10-17`, `complianceProjection.ts`) minus `MANDATE_LEAD_DAYS` (47) = `2026-08-31`, with `SDC_SIMULATED_NOW = 2026-08-31T12:00:00Z` (`src/services/sdc/clock.ts`). Fixture families are shifted onto per-family anchors (`shiftFields`); display states that depend on a date are computed at read (law 0.5, C11 V9/V10) and never stored; the suite pins its clock. `npm run drift` reports how far each family has moved from the wall clock; it is a report, not a gate. Since SRC-2 (#406) the RFQ and quotation fixtures are two more anchored families (`rfq`, `quotation`); before that every seeded open event read about a hundred days overdue. A quotation is judged against the event's response deadline at the declared present, while the day of an award, an advance, a conclude and a response is stamped from the browser clock (PR #407 records the mismatch; it is in `SE_BACKLOG_v3.md`). Since E2E-1 (#417) an exchange rate's age, its staleness refusal and its future-date check read the declared present too. Since PG-3 (#432) purchase orders are an anchored family (`FAMILY_ANCHORS.purchaseOrder`) and the sample ship notices share the orders' anchor, so the dashboard's Procurement row counts at the declared present; the order numbers still read `PO-2025-…` because a number is an identifier. A replica record's freshness is computed at the declared present and never stored (C13 §3), and a process-change version's stamps are the declared present (C1, FB-1). Consequence for the backend: never persist a projected status (`Expiring`, `Overdue`, `Delayed`, a publication line's OVERDUE); persist the date and let the read decide.

## 7 · Identity and sample users

There is no sign-in. `src/pages/auth/Login.tsx` picks a persona and seeds a seat; it collects no email and no password (removed at A1 and H3). The edge gate in front of the deployed app (`middleware.js`, `gate/`) is separate and does not know who you are inside the app.

The actor is `UNATTRIBUTED: NO_PERSON_IN_SESSION` unless the user opts into a **sample person**: one of 18 sample-person rows in `src/services/identity/sampleRoster.ts` (procurement ×2, receiving, finance, compliance, planning, requisitioner, buyer-all, admin, super-admin, supplier ×8 — 16 at the `handover-v2` tag, the two administrator rows added at ADM-1; the count is pinned by `src/handoverFigures.pin.test.ts`). Picking one makes `actor` `{ kind: 'RESOLVED', person: { personId } }`. `ActingPerson` is `{ personId }` only; labels are resolved at read (C10 D-ID-7). Verbs that need a named decider refuse an unattributed seat: PR approval (`PR_APPROVAL_ATTRIBUTED`), publication signing (`PUB_ACTOR_ATTRIBUTED`), module switching (`MODULE_SET_ATTRIBUTED`), delivery acts (`DELIVERY_ACTOR_ATTRIBUTED`). Added since v1: accepting or disputing a supplier's requirement response (SDC-3 ruling, #402); publishing, cancelling, awarding, advancing and concluding a sourcing event (`RFQ_ACTOR_UNATTRIBUTED`; raising a draft stays open); scoring a proposal (`SCORE_EVALUATOR_UNATTRIBUTED`). Payment release is refused to the named person who approved the invoice, and to an unnamed seat once the approval is named; an invoice approval by an unnamed seat is refused since OPS-2 (#411). Since SUP-1, FIN-1 and E2E-1 (#414, #416, #417) the same holds for supplier-application, certificate, preferred-supplier, material-request, role-grant, stock-record and default-cap decisions, for approving or rejecting a requisition, for publishing, discarding or withdrawing a forecast publication, and for accepting, part-accepting or rejecting a goods receipt; `sup1NamedSeat.test.ts` holds the list both ways, and D6 §2 lists the acts still open. Since ADM-1 (#420) creating a goods receipt refuses a seat that names nobody (`GR_RECEIVER_UNATTRIBUTED`) and stamps `receivedByPerson` and `receivedAt`. Since the Flow Builder every act on a process change and on an added step needs a named person. A sample person is marked as sample wherever rendered, may not accept governance risk (C10 §6.3a), and on the production deployment may not switch modules (`MODULE_SET_NOT_SAMPLE_IN_PROD`, `src/services/modules/deployment.ts`), may not approve, activate or restore a process change (`FLOWVERSION_SAMPLE_IN_PRODUCTION`), and is not exempt as a Super Admin (PR #420). The Super Admin exemption belongs to the role id, not to a permission: a custom role copied from `super_admin` gets the permissions and not the exemption (PR #420).

## 8 · Gates and the floor

`npm run gates` (`scripts/gates.mjs`) runs exactly four checks, in order, and asserts each did something:

1. `npm run build` (guides, `tsc`, `vite build`), and asserts a bundle was emitted;
2. `tsc -p tsconfig.vitest.json --noEmit`, the typecheck of the spec files, and asserts the `"exclude": []` override is present;
3. `npx vitest run`, and asserts the collected test and file counts are at least the **floor** in `scripts/floor.json` (9,464 tests across 517 files at the pin, 8,686 / 481 at the v2 tag; a floor, not an equality);
4. `npm run test:gate`, the edge-gate suite in `gate/` (floor 7 tests).

CI (`.github/workflows/gates.yml`) runs this one command on every pull request whatever its base (`types: [opened, synchronize, reopened, edited]`), on every push to `main`, and daily at 00:17 UTC. `CLEAN` on a PR is not evidence; read the check list by name. The suite no longer depends on the clone directory's name (PR #375). Not re-measured in this refresh: full-suite duration and the two whole-tree scans that timed out under load on 2026-09-25. Several pull requests since the v2 tag record a local gates run that did not complete on a memory-starved machine: in #430 the combined `npm run gates` was cut off by the machine's memory reaper, and in #431 the suite step inside it failed on worker timeouts while the same files passed alone; both name CI's run as the gate record. #438 records two 5-second timeouts in one full suite run on the same kind of machine, with `npm run gates` green on the merged tree. Run the suite with nothing else running. Two timing notes from the review week, both from the PRs and not re-run here: the intake view's first render over the whole population carries an explicit 15 s timeout by ruling (PLN-4, #398), and `personNamingRefusal.test.ts` timed out once at 5,000 ms inside `npm run gates` and passed on every other run (RFx-2 state note).

## 9 · The derivation discipline, in plain words

- **Derive populations; never work an inherited list.** The census helpers (`looseEndCensus.ts`, `WIRED_COMMAND_TARGETS`, `ALL_CAPABILITIES`, `catalogRoles()`, `GUIDES`, `MODULE_CODES`) exist for this.
- **A suspiciously small or round result is a bug in the matcher.** Assert a known-true member is present and a known-false one absent before believing any census.
- **Do not restate counts in prose** unless a test re-derives them on every run (C1 is the model).
- **Probe a guard both ways.** Assert a known-good input passes before trusting a known-bad failure.
- **A clean result taken right after a fix is a report about the fix.** Fire a new gate at the defect it was written for.
- **Before an irreversible act** (merge, push, publish, delete), assert the object exists at the site the action names.

## 10 · How to add a verb, end to end

1. **The edge.** Add a `TransitionDef` to `src/services/transitions/flows/<entity>.flow.ts`. If the entity is new, add the flow file, register it in `src/services/transitions/index.ts`, and declare `terminals`. (This is the only way to add a verb, a state or a flow. The Flow Builder adds steps in front of existing acts and cannot add any of the three, §2.7.)
2. **The atom.** Put the atom in the right lane bundle in `businessRoles.ts`; `businessRoles.test.ts` fails until every atom is held by some lane.
3. **The module.** Make sure the verb's entity belongs to a module in `src/services/modules/registry.ts`, so `MODULE_INACTIVE` can reach it.
4. **The target.** If the entity has no `CommandTarget`, add one in `MockCommandService.ts` and register it in `TARGETS` in the same commit.
5. **The hook.** Add a key to `POLICY_HOOKS` and its binding in `policies.ts`; read the document through `target.readEntity`. A check that separates two persons asks `exempt?.(head)` where it would refuse, and the refusal that names a person is keyed by its head so a surface renders its own copy (`personNamingRefusal.test.ts`).
6. **The hook for the page.** Add a mutation in `src/services/query/commandHooks.ts` (or the `sdc*Hooks` family) that calls `svc.commands.dispatch(...)` and invalidates the scoped keys.
7. **The surface.** Wire the control with the shared components (§11); render `HandoffNotice` for seats that cannot fire it; toast only what happened (the two toast gates will check). If the process is one whose surface can show an added step, ask `useNextAct('<entity>')` and mount `NextActLine`, and add the entity to `STEP_SURFACES`: `liveWorld.test.ts` holds that list equal to the `useNextAct` calls in the source, both ways.
8. **The guide.** Add the verb's block to `docs/guides/<entity>.en.md` and `.id.md`, in registry order; `guides.test.ts` fails otherwise.
9. **Locale.** Add EN and ID strings in `src/lib/i18n/`.
10. **Run `npm run gates`.** If C1 goes red, update `docs/contracts/C1-methods.md` and let the pin agree, never the other way round.

## 11 · The shared UI components and their gate (new in v3; PRs #421–#432)

Between the v2 tag and this pin every page was moved onto one set of components, and a gate (`src/lib/uiGate/`, `derive.ts` and `grandfathered.ts`) holds it. A page states *what* a thing is; the component decides how it looks. `className` on a shared component is layout only (a width, a margin).

| Thing | Component (`src/components/ui-v2/`) | Rule the gate holds |
|---|---|---|
| a table | `DataTable`: a column states its kind (`id`, `text`, `number`, `money`, `date`, `status`, `actions`) and the kind fixes the cell's type and alignment; the column that names the row is semibold | no hand-written table outside `RAW_TABLE_GRANDFATHERED`; no cell dresses itself |
| a list page | `ListPage`: header, count line, notices, figures, tabs, filters, search, content, in that order | a routed page that draws a table uses it |
| a fact on a drawer or a detail page | `Field` in `FieldList`; a heading is `SectionHeading`, `level="section"` or `"group"` | no `<dl>`/`<dt>`/`<dd>`, no `<h2>`…`<h6>` outside the shared components; a field is never tinted or boxed by its page |
| a form | `TextInput`, `Select`, `TextArea`, `Checkbox`, `Radio`, `ChoiceCard`, `FormField`, `FieldLabel` (`Form.tsx`); every control is 40 px | no `<input>`, `<select>`, `<textarea>`, `<label>` outside them, except the files named in `RAW_CONTROL_EXEMPT` |
| a box | `Card` (`padding`, `tone="inset"`, and the states `accent`, `fill`, `highlighted`) or `Notice` (a left rule on a tint; `tone="sample"` is neutral and dashed) | no element draws its own border-and-radius or left rule, including through a class constant (`RAW_BOX_GRANDFATHERED` lists what still does, with reasons) |
| something pressed | `Button` (40 px), `LinkButton`, `IconButton`, `ToggleChip`, `RowButton`, `CardButton`; a chip is `StatusPill` | no `<button>` outside them, except `RAW_BUTTON_EXEMPT` |
| a pop-up | `Dialog` (`fill` is full-screen, `anchor` hangs it from a control) or the drawer `SidePanel` (`wide` holds a table) | `role="dialog"` is written in those two files only |
| tabs that own a panel | `Tabs` (per-tab id, test id, `aria-controls`) | — |
| a grade | `GradeBadge`, `GradeChip` | one ramp, in tokens |
| a chart's text | `lib/chartPalette.ts` (`CHART_TICK`, `CHART_LEGEND_STYLE`, `CHART_TOOLTIP_STYLE`, `chartLabel`) | 11 px is the smallest type the portal renders |

**Tokens.** Text and fill are separate tokens wherever the fill fails as text: links and button labels take `action-text`, teal words `teal-text`; `action` and `teal` are fills, borders and icons. The red token is `critical` (the TypeScript variant name `'danger'` on `StatusTone` and `StatusPill` is unchanged). SAMPLE, ILLUSTRATIVE and SIMULATED markers take the neutral, dashed `sample` token; amber is for real warnings only. The heaviest weight is semibold. `TYPE_GRANDFATHERED` and `COLOUR_GRANDFATHERED` are empty; the exemptions are named files in `TYPE_EXEMPT` and `COLOUR_EXEMPT` (the chart palette and the messenger demo).

**Buttons.** `Button`'s default is `outline`. A page's main action is the one solid primary button on the page (UI-1d). Inside a drawer, a wizard or a dialog the final commit is the one solid button (UI-1e); a destructive final commit is a solid critical button, and the first press that only asks is the critical outline (PG-1). How many solid buttons stand in a container is counted by the container at render (`oneSolid.ts`): thrown in development and in every spec, logged in a production build. A drawer state that no spec and no walk opens has never been counted (PRs #429–#431).

**Derive, do not quote.** What is still exempt or hand-written is in `grandfathered.ts` and the `*_EXEMPT` lists in `derive.ts`; each row states its reason, and no count is written here. AG Grid (SE-1) is a third-party engine and will need its own theme to these tokens.
